# ASSURED — архітектура MVP

Документ для команди: як побудована система, як вона працює та чому ми обрали саме такі рішення.

---

## 1. Що ми будуємо

**ASSURED** — платформа пішохідної мікронавігації для кур'єрів. Автомобільні навігатори доводять до будинку, але не до дверей: вони не знають, де вхід у під'їзд, які двори перекриті, де шлагбаум чи розкопана доріжка.

MVP закриває чотири речі:

1. **Казуси (перешкоди)** — кур'єр позначає на карті проблему (закрито, ремонт, собака, шлагбаум), інші кур'єри бачать її й підтверджують або спростовують.
2. **Маршрут до дверей** — пішохідний маршрут, який обходить актуальні казуси.
3. **Робота за поганого зв'язку** — застосунок лишається корисним у під'їздах, підвалах і дворах без мережі.
4. **Фоновий трекінг** — вимірюємо реальний час від входу в зону адреси до дверей. Це основна метрика пілоту.

## 2. Загальна схема

```
┌──────────────────────────┐        HTTPS / JSON        ┌───────────────────────────┐
│  Мобільний застосунок    │ ─────────────────────────► │  API (NestJS)             │
│  Expo / React Native     │ ◄───────────────────────── │  чиста архітектура        │
│                          │                            │                           │
│  • карта (Mapbox)        │                            │  auth · obstacles         │
│  • офлайн-черга          │                            │  entrances · routes       │
│  • фоновий трекінг       │                            │  addresses · visits       │
└──────────────────────────┘                            └──────┬───────────┬────────┘
            ▲                                                   │           │
            │ спільні типи й схеми                              │           │
            ▼                                                   ▼           ▼
   ┌──────────────────┐                              ┌────────────────┐ ┌──────────────┐
   │ packages/contracts│ ◄── використовує і API ──── │ PostgreSQL +   │ │ Valhalla     │
   │ (zod-схеми)       │     і мобільний клієнт      │ PostGIS        │ │ (маршрути)   │
   └──────────────────┘                              └────────────────┘ └──────────────┘
                                                                         ┌──────────────┐
                                                                         │ Photon       │
                                                                         │ (геокодер)   │
                                                                         └──────────────┘
```

Монорепозиторій на **pnpm**:

| Пакет | Призначення |
|---|---|
| `apps/api` | Бекенд на NestJS 11, Drizzle ORM, Postgres + PostGIS |
| `apps/mobile` | Мобільний застосунок на Expo SDK 57 (expo-router, TanStack Query, zustand) |
| `packages/contracts` | Спільні zod-схеми запитів і відповідей |

### Чому монорепо і `contracts`

Клієнт і сервер описують одні й ті самі дані. Якщо схема лежить в одному місці, то зміна поля ламає збірку відразу в обох застосунках, а не в проді. zod-схема водночас є типом (TypeScript) і валідатором (під час виконання), тож один опис працює і на сервері, і на телефоні.

## 3. Бекенд: чиста архітектура

Кожна фіча (`obstacles`, `routes`, `visits` тощо) розкладена на чотири шари:

```
presentation   контролери, DTO, guard-и, interceptor-и   (HTTP-світ)
     │
application    use case-и та порти (інтерфейси)          (сценарії)
     │
domain         сутності, правила, помилки                (чиста логіка)
     
infrastructure Drizzle-репозиторії, Valhalla, Photon     (деталі, реалізують порти)
```

**Правило залежностей:** усередину, до домену. Домен нічого не знає про NestJS, Postgres чи HTTP. Application говорить із зовнішнім світом лише через **порти**, а infrastructure їх реалізує.

Це не лише домовленість: ESLint-плагін `boundaries` забороняє application імпортувати чужі домени (дозволені лише власна фіча й `shared`). Порушення правила не проходить лінтер.

### Чому саме так

- **Заміна зовнішніх сервісів без переписування логіки.** Публічний Photon — тимчасове dev-рішення. Use case-и залежать лише від порту `Geocoder` (метод `search(query, near?)`), а Photon — це один адаптер `PhotonGeocoder`, який підключається одним рядком у `addresses.module.ts`. Заміна виглядає так:
  1. Свій Photon: піднімаємо контейнер з даними по Україні й змінюємо `GEOCODER_URL`. Код не чіпаємо.
  2. Інший провайдер (Mapbox, Nominatim, Pelias): пишемо новий клас, що реалізує `Geocoder` і приводить відповідь до `AddressSuggestion`, та міняємо `useClass` у модулі. Use case-и, контролер і мобільний застосунок лишаються без змін.

  Застереження: це стосується лише пошуку адреси для маршруту на сервері. Підказки вулиць при реєстрації зараз ходять у Mapbox напряму з мобільного застосунку, тож їх треба перевести на наш API, щоб геокодер змінювався в одному місці.
- **Тестованість.** Логіку можна перевіряти без бази й HTTP.
- **Межі між фічами.** Маршрутизація потребує казусів і входів, але не залежить від їхніх доменів: `routing` має власні порти (`RouteObstacleSource`, `EntranceFinder`), а мости до інших фіч розташовані в infrastructure. Так фічі лишаються незалежними, а в майбутньому їх легше винести в окремі сервіси.

### Модулі API

| Модуль | Що робить |
|---|---|
| `auth` | Реєстрація, логін, JWT access/refresh, ролі, tenant |
| `obstacles` | Створення казусів, підтвердження/спростування, TTL, фільтри за bbox |
| `entrances` | Входи в під'їзди, прив'язані до адреси |
| `routes` | Побудова маршруту через Valhalla з обходом казусів |
| `addresses` | Пошук адрес і геокодування |
| `visits` | Візити доставки, події та точки треку |

### Multi-tenant із першого дня

У таблиці `users` є `tenant_id`, а також `role` (кур'єр, адмін тощо). Для пілоту це один клієнт, але додати другого можна без міграції даних. Закладати це на початку дешево, а переробляти пізніше дорого.

### Ідемпотентність

Мобільна мережа ненадійна, тому запит може піти двічі: застосунок не отримав відповідь і повторив. Усі записи, чутливі до дублів, приймають заголовок `Idempotency-Key`:

- клієнт генерує ключ один раз на дію й зберігає його разом із діє в черзі;
- сервер зберігає пару (користувач, ключ) → відповідь, і повторний запит повертає ту саму відповідь без повторного ефекту.

**Чому це критично:** без ідемпотентності офлайн-черга створювала б дублікати казусів і точок треку при кожному збої мережі.

## 4. Казуси та маршрути

### Життєвий цикл казусу

- Створюється кур'єром із координатами, типом і необов'язковим коментарем.
- Інші кур'єри **підтверджують** або **спростовують** його. Коли кількість спростувань досягає порога `OBSTACLE_DISMISS_THRESHOLD`, казус знімається.
- Казус має **TTL** (`INCIDENT_TTL_SEC`): якщо ніхто не підтверджує, він застаріває сам. Так карта не засмічується неактуальними даними.
- Пошукові запити фільтрують за bbox через PostGIS, тож індекс працює на великих обсягах.

### Побудова маршруту

1. Адреса призначення геокодується (**Photon**).
2. Сервер знаходить відомий вхід у під'їзд (`entrances`) або використовує точку адреси.
3. Активні казуси поблизу перетворюються на `exclude_polygons`.
4. **Valhalla** (пішохідний профіль) будує маршрут в обхід цих полігонів.
5. Відповідь містить polyline6, відстань і час.

**Чому Valhalla:** вона open-source, має готовий пішохідний профіль і підтримує `exclude_polygons`, що саме нам і потрібно для обходу казусів. Дані OSM розгортаються у власному контейнері (профіль `routing` у docker-compose), тож ми не залежимо від зовнішнього API і не платимо за кожен запит.

На мобільному клієнті маршрут **перевіряється раз на 25 секунд** і після кожного запису казусу. Якщо інший кур'єр щойно позначив перешкоду на шляху, маршрут оновиться, а користувач побачить індикатор «маршрут оновлюється».

### Захист від «маршруту на 14 км»

Раніше помилка геокодування профілю давала маршрут не в те місце. Тепер при реєстрації місто вибирається зі списку (понад 1300 міст України з пошуком, без запитів до мережі), а адреса перевіряється на відповідність обраному місту (`resolveAddressPoint`). Якщо точка потрапляє явно не туди, реєстрація не проходить мовчки.

## 5. Мобільний застосунок: FSD

Структура за **Feature-Sliced Design**:

```
app/        екрани та навігація (expo-router)
features/   сценарії користувача: map, obstacles, obstacle-create, route, auth, tracking
entities/   доменні сутності: obstacle, route, session
shared/     api, i18n, UI, утиліти, дані
```

Правило: шар залежить лише від нижчих. **Фічі не імпортують одна одну** — їх збирає екран у `app/`. Це перевіряє лінтер.

**Чому FSD:** застосунок швидко росте, і без меж фічі починають залежати одна від одної. Тут можна змінити трекінг, не зачепивши карту, а нову фічу додати окремою папкою.

### Стан

- **TanStack Query** — серверний стан (казуси, маршрут, візити): кеш, повторні спроби, оптимістичні оновлення.
- **zustand** — локальний стан (чернетка казусу, офлайн-черга, сесія).
- Локалізація: `i18next` (укр / англ).

## 6. Поганий зв'язок і офлайн

Кур'єр часто працює без мережі: ліфт, під'їзд, підземний паркінг. Тому **офлайн — основний режим, а не виняток**.

| Проблема | Рішення |
|---|---|
| Створення казусу без мережі | Пишеться в **локальну чергу** на диску з власним `Idempotency-Key`; на карті одразу з'являється як «очікує синхронізації» |
| Мережа з'явилась | Черга відправляється автоматично, по порядку |
| Повтор після збою | Ідемпотентні ключі гарантують відсутність дублів |
| Казуси зникають при перебудові маршруту | Локальний сховок «відомих казусів» і розширений bbox запиту |
| Застосунок перезапустили без мережі | Токени очищаються **лише** при явній відмові сервера (400/401/403), а не при будь-якій помилці; профіль береться з локального кешу |
| Файлова система | Атомарний запис (tmp-файл + move), щоб збій посеред запису не пошкодив дані |

Окремо: **помилки мережі й помилки сервера розрізняються** (`isNetworkError`, `isTransientError`). Тимчасові помилки повторюємо, а постійні (наприклад, 4xx із валідацією) відкидаємо, щоб одна «погана» дія не блокувала всю чергу.

## 7. Фоновий трекінг

Мета: виміряти реальний час від входу в зону адреси до дверей.

### Як працює

```
Старт доставки ──► груба стеження (~кожні 50 м, економно)
                          │
              перша точка ≤ 300 м від адреси
                          │
                          ▼
        подія «arrived_at_house» + точний режим (кожні кілька метрів)
                          │
              кнопка «Я біля дверей»
                          │
                          ▼
        подія «reached_door» → візит завершено, запис зупинено
```

### Рішення та причини

- **Два режими точності.** Далеко від адреси нам достатньо грубого сигналу (економія батареї), а точні дані потрібні лише в зоні 300 м (`TRACK_RADIUS_M`). Це ключовий компроміс між батареєю й якістю даних.
- **Фільтр якості.** Точки з похибкою гірше 65 м і поза зоною не записуються: вони лише шумлять і збільшують обсяг.
- **Спочатку на диск, потім на сервер.** Фонове завдання може жити секунди, а телефон може втратити мережу. Тому кожна подія й точка спершу зберігається локально, а відправляються вони пачками по 200 у правильному порядку. При першій помилці відправка зупиняється й повторюється через 20 секунд.
- **Ідемпотентність на сервері.** Унікальність `(visit_id, recorded_at)` не дозволяє дублювати точки при повторній відправці, а ідентифікатор візиту генерує телефон, тож старт безпечно повторювати й він працює офлайн.
- **Перша подія перемагає.** Повторні події не перезаписують уже зафіксований час.
- **Захист від сміття.** Точки з часом понад 5 хвилин у майбутньому ігноруються. Покинуту доставку автоматично скасовано через 12 годин.
- **Окрема реєстрація фонового завдання** у кореневому layout, щоб система могла розбудити застосунок заради нової координати.

### Приватність

- Перед першим стартом користувач **явно погоджується** на запис геолокації.
- Записуються лише точки поблизу адреси доставки, а не весь день кур'єра.
- Сирі точки автоматично видаляються через `TRACK_RETENTION_DAYS` (за замовчуванням 30), а записи візитів із часами лишаються для метрик.
- Доступ до візиту має лише його власник.

## 8. Інфраструктура

Усе піднімається через `docker-compose`:

| Сервіс | Роль |
|---|---|
| `db` | Postgres + PostGIS |
| `api` | NestJS (порт 3550 → 3000) |
| `valhalla` | Маршрутизація, профіль `routing` (опційно, окремо через `--profile routing`) |

Міграції — Drizzle (`0001` tenants/ідемпотентність, `0002` казуси та входи, `0003` візити та треки), застосовуються окремою командою. Конфіг — через env із валідацією схемою на старті: сервіс не запуститься з некоректними налаштуваннями.

## 9. Ключові рішення коротко

| Рішення | Чому |
|---|---|
| Чиста архітектура + `boundaries` | Незалежність від зовнішніх сервісів і фіч, перевірка правил лінтером |
| Спільні zod-контракти | Одне джерело істини для клієнта й сервера |
| Valhalla у власному контейнері | Підтримка обходу полігонів, без витрат на зовнішній API |
| PostGIS | Швидкі просторові запити (bbox, відстані) |
| Ідемпотентність скрізь, де є запис | Мережа ненадійна, повтор запитів неминучий |
| Офлайн-черга на диску | Кур'єр без зв'язку не втрачає дані |
| Два режими точності трекінгу | Баланс між батареєю і точністю |
| Multi-tenant + ролі з початку | Другий клієнт без переробки даних |
| FSD на мобільному | Фічі розвиваються незалежно |

## 10. Що ще не зроблено / ризики

- **Фото казусів** — у БД є колонка `photo_key`, але завантаження не реалізоване.
- **Публічний Photon** — лише для розробки; для продакшну потрібен власний геокодер. Заміна: або власний Photon (змінити `GEOCODER_URL`), або новий клас, що реалізує порт `Geocoder`, і зміна одного рядка в `addresses.module.ts`.
- **Два геокодери.** Пошук адреси для маршруту йде через наш API (Photon), а підказки вулиць при реєстрації в мобільному застосунку ходять напряму в Mapbox. Їх варто звести до одного місця (через наш API), щоб геокодер змінювався в одній точці.
- **Фонова поведінка на реальних пристроях** потребує польових випробувань: iOS і Android по-різному обмежують фонову геолокацію. Для роботи потрібен дозвіл «Завжди»; з дозволом «Під час використання» запис іде лише при відкритому застосунку.
- **«Дійшов до дверей»** — поки лише ручна кнопка. Виміряний час іде від входу в зону 300 м до цього натискання. Автовизначення за відстанню до відомого входу можна додати пізніше (рішення за продуктом).
- **Параметри для узгодження з продуктом:** радіус зони 300 м, поріг точності 65 м, автоскасування 12 год, зберігання 30 днів.
- **Наступні етапи:** мінімальна адмінка (клієнти, кур'єри, список казусів із видаленням, вивантаження метрик пілоту) і підготовка пілоту.
